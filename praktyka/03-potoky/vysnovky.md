# Практична 03 — висновки

У мене AMD Ryzen 5 5600H: 6 фізичних і 12 логічних ядер (`os.cpu_count()` = 12), Windows 11, Python 3.13.3 з увімкненим GIL.
На обчисленнях Мандельброта послідовна версія працює 6,12 с, а 2, 4, 8 і 12 потоків дали прискорення лише ×1,03, ×0,97, ×0,97 і ×0,97, тобто потоки нічого не прискорили (на 12 потоках один прогін навіть тривав 8,39 с).
Відношення процесорного часу до настінного для 8 потоків — 0,96: програма запустила вісім потоків, а в кожен момент працювало в середньому лише одне ядро.
Причина — GIL (Global Interpreter Lock): у CPython виконувати байт-код може тільки той потік, який тримає цей замок, тому потоки на чистому Python рахують по черзі, а не одночасно, і ще трохи часу витрачають на передачу замка один одному.
Задача з очікуванням прискорилась майже в стільки разів, скільки потоків (×2,0 для 2, ×15,9 для 16, ×31,6 для 32 — 0,51 с замість 16,01 с), бо під час `time.sleep` потік відпускає GIL і процесор йому не потрібен: відношення процесорного часу до настінного тут лише 0,016.
Тому на графіку крива обчислень лежить біля 1 (її обмежує один GIL, а не кількість ядер), а крива очікування йде вгору майже по діагоналі (її обмежує лише кількість одночасних очікувань).
Для прискорення своєї задачі я оберу процеси (`ProcessPoolExecutor` / `multiprocessing`): у кожного процесу свій інтерпретатор і свій GIL, тож вони справді зможуть зайняти всі ядра, а потоки варто залишити для задач з очікуванням (мережа, файли).
